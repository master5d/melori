# melori contributor guide

melori is a local-first copilot for one-to-one consultation calls, held with the client's written consent. It is a fork of echo/Handy: a Rust/Tauri shell with a React frontend, plus a local Python engine in `engine/` (clients, per-kind consent, sessions, psychology council) that the shell starts on loopback with a per-run token.

Fork rule: the inherited echo core (ASR engines, audio capture, `src-tauri/src/managers`, `src-tauri/crates/echo-audio`, `echo-core` inference) is changed only additively; melori code lives in `engine/`, `src-tauri/crates/melori-consult`, `src-tauri/src/consult` and `src/consult`. Client data never enters the repository.

## Development

Install Node.js 20+ and stable Rust, then run `npm install`, `npm run dev`, `npm run build`, `npm run lint`, and `npm run test:unit`. The desktop application is built with `npm run tauri dev` or `npm run tauri build`. Native workspace tests can be run with `cargo test --offline --workspace --exclude echo` from `src-tauri`.

## Architecture

- `src/` contains the React UI, stores, bindings, and translations.
- `src-tauri/src/` contains the Tauri application and platform integration.
- `src-tauri/crates/echo-config` owns persisted settings and shared types.
- `src-tauri/crates/echo-core` owns model discovery, downloads, and inference.
- `src-tauri/crates/echo-text` owns language and formatting logic.
- `src-tauri/crates/echo-audio` owns capture, monitoring, and audio analysis.
- `src-tauri/crates/echo-voice*` owns local and optional voice playback.
- `src-tauri/crates/melori-consult` (Tauri-free, natively tested) owns the engine supervisor, the UI→engine path allowlist and the client-meeting binding; `src-tauri/src/consult` wires them into Tauri.
- `engine/` (Python, FastAPI) owns clients, consent, sessions, note templates, note generation, the council and the HTTP API. A session is a folder `clients/<id>/sessions/<sid>/` (`meta.json`, `transcript.jsonl`, `notes/NNN.json` versions that are never overwritten, `runs/NNN.json`, `email.json` — the current follow-up email draft, generated `session.md`); old single-file sessions are migrated on first read and keep their source as `legacy.md`. The configured model may ignore `response_format`, so note parsing accepts fenced JSON and Markdown sections. Per client (only with `retain`): `index.sqlite` (fragments, FTS5 over word stems — Russian fleeting vowels by rule in `practice/index.py`, float32 vectors from `MELORI_EMBED_MODEL`), `chats/NNN.json`, `recap.json`; always close a `ClientIndex` — an open `index.sqlite` blocks deleting the client folder on Windows. Meeting asks go to `asks.jsonl` (only with `retain`); note versions carry `warnings` from `practice/diagnosis.py`; moment marks travel as segments with `source: "mark"`. tauri-specta event names are the kebab-case struct name (`MeetingVoiceEvent` → `meeting-voice-event`) — keep hand edits of `src/bindings.ts` to that rule; test with `engine/.venv/Scripts/python -m pytest engine/tests`. `engine/tests/dump_contract_fixtures.py` regenerates `src/consult/__fixtures__/`, which `src/consult/api.contract.test.ts` checks the UI against — rerun it after any API change.
- `src/bindings.ts` is generated by specta, on request only: `MELORI_EXPORT_BINDINGS=1 npm run tauri dev` regenerates it (a plain `tauri dev` leaves it alone). Payloads of plain `app.emit` events are registered with `.typ::<T>()` in `lib.rs`, so the file never needs hand edits.
- Tests of the `echo` app crate itself do not start on Windows (`STATUS_ENTRYPOINT_NOT_FOUND`); check it with `cargo check -p echo` and keep testable logic in leaf crates.

User-facing strings belong in i18next and every new translation key must be present in all locale files. Keep the application local-first: network access must be explicit, bounded, and opt-in. Model entries with no official source are available only through the user-configured model mirror.

Do not commit credentials, private endpoints, machine paths, generated build artifacts, or session data. Do not change `LICENSE` without an explicit maintainer decision. Keep changes focused and run the relevant tests before opening a review.
